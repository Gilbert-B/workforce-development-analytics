## B. Recommended target architecture

### B1. Shared model or separate models: recommendation

**One shared semantic model folder used by three reports through `byPath`, developed locally. The path to a published shared model stays open, without depending on it.**

| Option | How | For | Against | Verdict |
|---|---|---|---|---|
| **1. One model, several reports (`byPath`)** | each report folder's `definition.pbir` points to the same `*.SemanticModel` folder | one set of tables, relationships and DAX; works fully offline in Desktop; Report 01 unchanged | Desktop opens the full model with every report (no true "thin" report locally); only one Desktop window should edit at a time; a measure created while in Report 02 is saved into the shared model | **Recommended** |
| 2. One model per report | three `*.SemanticModel` folders | each report independent and smaller | duplicates dimensions, relationships and DAX (breaks constraint 2); definitions drift | Rejected |
| 3. Published model + live-connected thin reports (`byConnection`) | publish the model once to a Power BI workspace; reports connect live | true thin reports; one refresh; the standard enterprise pattern | needs Power BI Service sign-in and, for sharing, Pro or Fabric licences; the owner has no organisational tenant | **Future option** only; the PBIR can be re-pointed with one setting |
| 4. Composite model (DirectQuery to a published model) | each report extends the published model | flexible | needs the Service; more complex than this project requires | Rejected |

**Why option 1 still demonstrates a governed, shared model:**
- every report uses the **same** tables, relationships and measures;
- each business definition exists exactly once, in TMDL, in Git;
- the move to option 3 later changes one setting per report (`byPath` → `byConnection`), with no model or DAX change.

### B2. How the reports connect and refresh
- **Connection:** each report opens the shared model folder. The model imports from `localhost` / `WorkforceDevAnalytics` (the `rpt` views only, as now).
- **Refresh:** refreshing in *any* report refreshes the **one** shared model, and its local cache (`SemanticModel/.pbi/cache.abf`, never committed) is shared too. Refresh once, and all reports show the same data.
- **Rules:**
  1. **One Desktop window at a time** on the suite. Two windows on the same model folder could overwrite each other's saves.
  2. **Measures live in the model, organised by domain** (display folders `Training`, `Coaching & Watch-list`, `Certification`, `Readiness`, `Operations`, `Outcomes`). A measure added while in Report 02 *is* a shared definition, so it goes through the same review as any other.
  3. **The model changes only additively** (no renamed or removed tables, columns, relationships or measures) unless separately approved. A new automated check enforces this (C4).

### B3. Model size and performance (with future operational data)
- **Expected Build 03 volume:** a few hundred associates × a few thousand payment cases each ≈ **0.5–1 million case rows**, plus case events and QA samples of a few million rows. That's comfortable for an Import model in Power BI Desktop on a normal laptop: expect a model of a few hundred MB and a refresh of a few minutes.
- **Design rules for Build 03:**
  - SQL `rpt` views provide a **daily aggregate fact** for trends and command-centre tiles, plus a case-grain fact for drill-down. Desktop never aggregates millions of rows per visual.
  - Integer surrogate keys on large facts; no high-cardinality text columns imported unnecessarily (for example case notes).
  - `dim_date` gets additive bounds so it covers the operational dates.
- **Limit:** there is no incremental refresh locally (that's a Service feature), so every refresh is full. Keeping synthetic volumes moderate is a deliberate, documented choice.

### B5. Navigation and the product family
- **Within a report:** the existing rail pattern, the same in all three reports (position, icons, Clear filters / Reset view behaviour, a synced cohort or team selection, the "Data as of" pill).
- **Between reports:**
  - **Local limitation:** Power BI page navigation only works *within* one report; Desktop can't jump from one `.pbip` to another.
  - **What we build:** each report gets a small "Workforce Intelligence Suite" switcher in its rail, plus an About-page block naming the sibling reports and what each is for.
  - **Later:** when published to the Service, the same buttons take **web URL** actions, or the three reports form one Power BI **App** with its own navigation.
- **Distinct but related identity:** all three use `suite-tokens.json`, which fixes the type scale, spacing grid, semantic colours (good / warning / bad / unrecorded), the KPI tile anatomy and the snapshot labelling. Each report then sets its own surface:

| Report | Look |
|---|---|
| Report 01 | dark premium (unchanged) |
| Report 02 | light command-centre: white and slate, high-contrast status colours, dense tiles |
| Report 03 | analytical: off-white, serif headings, generous annotation space |

- **Accessibility, shared:**
  - contrast of at least 4.5:1 for text;
  - status never shown by colour alone (labels or icons too);
  - alt text on KPI cards and images;
  - a logical tab order (already generated);
  - "blank ≠ zero" conventions documented once.

### B6. Publishing (local-first, no paid infrastructure)
**The portfolio release is:**
- the GitHub repository (PBIP source, SQL, Python, docs);
- the recorded walkthrough video already agreed;
- screenshots;
- the website case study.

None of these need a Power BI licence.

**Optional, if a Service account becomes available:**
- publish the shared model **once**, from Report 01;
- re-point Reports 02 and 03 to it with `byConnection` and publish them;
- package all three as an App.

**Risk to avoid:** publishing each `byPath` report directly would upload **three copies** of the model.

### B7. Limitations and risks
| Risk | Mitigation |
|---|---|
| Two Desktop windows saving the same model | working rule (one at a time), plus `check_model_additive.py` and `git diff` review before every commit |
| Accidental breaking edit to the shared model while working on Report 02 | additive-only check against the last validated tag, run in CI-style before commit (C4) |
| `byPath` multi-report behaviour depends on the Desktop version | **ARCH-01 spike**: you open a minimal Report 02 shell on your Desktop before any real build |
| One model grows large | daily aggregate facts in SQL, moderate synthetic volumes, no unneeded text columns (B3) |
| Field list becomes crowded for each report's author | domain display folders, hidden technical columns, optional TMDL *perspectives* per report |
| No cross-report click-through locally | suite switcher text + About block now; web URLs or an App only if published |
| Snapshot too early for operational and outcome analysis | decision **E1** |

### C2. Create for Report 02 (BI-03)

**Prerequisites:** BI-02 merged, plus ARCH-01.
- **The report:** `payment-operations.pbip` + `PaymentOperations.Report/` (thin, `byPath`) and the light theme `PaymentOperationsLight.json`.
- **Generator split:** `pbir_lib.py` extracted from the Report 01 builder, **proven by regenerating Report 01 byte-identically**; then `build_payment_operations.py`.
- **Additive model objects:**
  - operations `rpt` views (deployment / assignment, case, case event, QA review, SLA policy, daily aggregate);
  - conformed relationships through `dim_enrolment`, `dim_employee` and `dim_date`, plus new dimensions (team / queue, case type, SLA tier);
  - an *Operations* measure folder, reviewed by ChatGPT like BI-02.

### C3. Wait until Report 03 (BI-04)
- `WorkforceOutcomes.Report/` and its theme;
- the outcome views (30/60/90-day windows, proficiency milestones, retention);
- training-vs-operations linkage measures;
- cohort-adjusted comparisons.

### C4. How we prove existing reports and measures still work
1. **Release tags.**
   - **`report01-v1`:** tagged on `main` after BI-02 merges.
   - **`model-v1`:** the validated model. Every later model change is compared against it.
2. **Additive-only model check** (`tools/check_model_additive.py`). It parses the TMDL on the branch and at `model-v1`, and fails if any existing table, column, relationship (or its direction or activity) or measure expression was removed or changed.
3. **Byte-identical Report 01.** Regenerating Report 01 after the helper refactor (and after every later change) must reproduce the committed files exactly.
4. **SQL reference scripts** stay the source of truth: Build 01 reference queries, `sql/bi02_measure_reference.sql`, and new `sql/bi03_measure_reference.sql`. The data-layer tests (133 now) keep passing.
5. **Model QA harness** (`model-qa.pbip`). A developer-only report on the shared model with one page per domain: a matrix of every measure by cohort or team, next to the expected value from the reference SQL. It **replaces the throw-away scratch pages** used for D26 and BI-02 and makes Desktop regression checks repeatable. It isn't a business or executive report, so constraint 7 holds.
6. **Owner Desktop checklist** per release: open each report, refresh once, and walk the QA pages plus a short smoke test of every page.

| Step | Scope | Exit criterion |
|---|---|---|
| **0. Close BI-02** | ChatGPT sign-off → PR → merge → tags `report01-v1`, `model-v1` | `main` holds the validated Report 01 |
| **ARCH-01** (small) | approve this proposal; decide E1–E4; spike: a minimal `PaymentOperations.Report` (`byPath`, one placeholder page) and `ModelQA.Report` opened on the owner's Desktop; `pbir_lib.py` extraction (Report 01 byte-identical); `check_model_additive.py`; `suite-tokens.json` | the owner confirms both reports open the shared model, refresh once, and Report 01 is unchanged |
| **Build 03**: payment operations data | **multi-source by design:** synthetic **case-management documents in MongoDB** (one payment-exception case per document, with nested events, QA checklist and rework history) → **Python ETL** (extract, flatten, validate, idempotent upsert, watermark-based incremental loads, rejected-row log) → SQL `stg` → `core` → `rpt`. Deployment and assignments come from readiness approvals; SLA and QA policy in config. Tests, audit outputs, reference SQL, Windows walkthrough | as Build 02: generator / ETL determinism, validation checks, owner Windows run |
| **BI-03**: Report 02 | operations tables, relationships and measures (ChatGPT DAX review); light command-centre pages (queue health, throughput, resolution time, accuracy / rework, QA, SLA, exceptions); suite switcher; QA-harness page | additive-only check passes; Report 01 byte-identical; owner Desktop validation |
| **Build 04**: outcomes data | 30/60/90-day windows from deployment, proficiency milestones, retention events, training-to-operations linkage views; cohort-adjusted comparisons computed in SQL/Python with explicit caveats (no causal claims) | as above |
| **BI-04**: Report 03 | analytical style; comparisons, explanatory annotations, storytelling pages | as above |
| **Final publication** | accessibility pass across all three reports; optional model-folder rename; README / architecture diagram; website case study; walkthrough video; optional Service publish (one model + App) | portfolio release |

**Why MongoDB → Python → SQL belongs in Build 03, and not as a checklist item:**
- **Case-management data is genuinely document-shaped:** variable-length event histories, QA checklists, rework loops.
- **Flattening it into a governed relational model** is a real data-engineering problem: grain decisions, late-arriving updates, idempotent incremental loads, data-quality rejections.
- **Training data (Builds 01–02) stays relational and simple,** because nothing would be gained by moving it.
- **Tooling:** MongoDB Community Server (free, local) or Docker, plus `pymongo`.
